The week the internet's elephant caught fire

In October 2026, two serious bugs in PHP, the language that runs about 7 in 10 websites, became public two days early. The bugs had been found with help from AI. Governments around the world switched off their own websites to protect them. This is the full story in plain language: where the bugs came from, who found them, how the secret got out, who went dark, who attacked, and what it means.

01 · The backstory

A 22-year-old crack in the foundations

To understand why one bug could darken government websites on three continents, you need to know what PHP is and why so much depends on it. You also need to know that people had seen this kind of weakness three times before.

What is PHP?

PHP is a programming language that runs on the web server, not on your phone or laptop. When you open a page, PHP fetches things from a database (your basket, a news article, a tax form), puts the page together, and sends it to your browser. Its mascot is a blue elephant, the "elePHPant".

It powers WordPress, Drupal, Joomla and MediaWiki (the software behind Wikipedia). It's also behind a huge number of council, ministry and university sites, which is why governments were hit so hard.

Everyday comparison

Think of the web as a city's restaurants. Your browser is the dining room. PHP is the kitchen at the back, cooking every page to order. PHP2Shell was a flaw in the standard kitchen design used by roughly 7 in 10 restaurants. It wasn't one bad chef. It was the floor plan itself.

That's why a page as simple as "Hello World" on an affected PHP version could be at risk. The problem was in PHP itself, not in any one website's code.5

Three warnings that came and went

The core idea behind PHP2Shell is simple: what happens when PHP runs out of memory halfway through a job? If it stops abruptly, it can leave half-finished work lying around, and later code may trust that mess. People had noticed this risk before.

2004 · The first sighting

On 14 July 2004, German researcher Stefan Esser (e-matters) published an advisory. He showed that a remote attacker could trigger PHP's memory_limit cut-off at an unsafe moment, leaving data half set up, and use that to run their own code. It was fixed in PHP 4.3.8 (CVE-2004-0594).25

Calif says Esser never published his exploit, and that this 2004 research was the starting clue for the 2026 hunt. Fittingly, Calif credits Esser with introducing them to the PHP Foundation's security engineer.4

2019/2020 · The second sighting

PHP bug #78876 showed that very long variables in a file-upload form could push PHP out of memory and leave cleanup undone.20

Sources disagree: Dead Neurons dates it to 2019 (CVE-2019-11048). Calif says 2020.204 Either way it was treated as a reliability problem, not a takeover risk.
2024 · The near miss

PHP's first external security audit was carried out by Quarkslab, coordinated by OSTIF and paid for by Germany's Sovereign Tech Agency. While fixing one of its findings, a PHP core developer "found the first signs" of the out-of-memory problem.3

Three fixes were proposed. One broke old code, one created a new way to crash sites, and one needed changes to thousands of add-ons. Because the team decided by consensus, nothing was agreed for months.23

"We won't pretend otherwise: the delay was a structural failure."PHP Foundation, explaining why the 2024 finding was never fixed. It blamed "both the security team's decision process and its lack of resources."236

Mihail Kirov, now at Tolmo, was on the 2024 audit team. He says the audit ran for 57 days with five people, and that its report noted "due to the time constraints of the audit, automated fuzzing was not utilized". One page of the report was withheld with the note "details to be shared after fixes are applied; fixes are complex and in progress". It stayed that way for about two years.22 The Wall Street Journal summed it up: this class of bug "had been flagged decades earlier" but was considered too hard to exploit.18

02 · The bug, explained without code

Two kitchen accidents

You don't need to read code to follow this. Both flaws come from one habit. When PHP runs out of its memory allowance, it stops on the spot instead of tidying up. Half-finished work gets left behind, and later steps trust it as if it were complete.933

CVE-2026-109618 · "RCE via OOM corruption"

The order slip abandoned mid-sentence

Picture a waiter writing an order slip. The kitchen suddenly runs out of counter space and everyone drops what they're doing. The half-written slip stays on the spike, and later the kitchen reads it as a finished order. If a stranger can arrange for that to happen, the "order" the kitchen follows can be theirs. In computer terms, that means their code runs on the server.3

The PHP Foundation warned that on some common setups this could happen "before any application code runs". In other words, the website's own code never gets a chance to defend itself.3

CVE-2026-109619 · "RCE via stale global state"

The hotel key that still opens the room

IBM's Patrick Fussell put it best: "Think of a hotel room where you check out, but your key still works."19 After a crash, PHP keeps internal "keys" pointing at memory from a previous visitor's request. The next request handled by the same worker can walk into that room and find what was left behind, such as passwords, login tokens or keys. Programmers call this a use-after-free.3

Severity

PHP rated both bugs 9.2 out of 10 (CVSS v4). The leak wrongly claimed 10.0. Wikipedia lists CVSS 3.x scores of 9.8 and 8.1.242

The fix

PHP turned its memory limit into a "soft" warning and added a separate hard ceiling at which the process is simply stopped. That way it never limps on in a broken state. The change touched an estimated 200 to 390 files, depending on the source.2418

Bug number three

On 23 Oct a related flaw, CVE-2026-115560, was disclosed. It affects even the patched releases and is due in the next regular update, not an emergency one. Agencies pointed to a temporary configuration workaround in the meantime.1021240

Why the name? "PHP" plus "shell", hacker slang for a command line on someone else's computer. Put together, it means "from a PHP web page to control of the whole server." Wiz Research coined it.51

03 · The AI angle

Did a robot really find it?

PHP2Shell was billed as one of the first world-scale bugs found with frontier AI. The truth is more interesting: humans pointed the AI in the right direction, and the AI did the heavy lifting at a speed people couldn't match.

Calif × OpenAI "Patch the Planet"

OpenAI launched Patch the Planet on 22 June 2026. It gives security teams access to its Codex Security tools and API credits so they can find and fix bugs in open-source software.91 On 30 July it invited the small red-team firm Calif to look at PHP.4

Researcher Ryan Austin worked with an "LLM companion" and a code-review agent, starting from Esser's 2004 clue. Calif says "no special harness or restricted-access models" were used, and adds: "No model is simply capable of unearthing 'all bugs' with simple prompts."4 OpenAI says the model was GPT-5.6 Sol.92

Wiz × Google Gemini

Wiz Research (Sagi Tzadik, Shir Tamari, Nir Ohfeld and Tomer Schwartz) started on 19 Aug. They confirmed takeovers of Drupal and then WordPress within two days, and reported on 24 Aug.5 They used their own tool, Atlas, together with Gemini 4 Argon and GPT-5.6 Sol. Gemini's contribution to building and checking the attack was "particularly significant".5

Wiz: "a single researcher completed in a week what previously would have taken a world-class team months of work".19

OpenAI Codex Security

OpenAI's own team, credited as "OpenAI Codex Security (Amy Burnett)", reported more ways in.31 OpenAI said: "To our knowledge, frontier AI found these vulnerabilities before attackers did" and called the episode "the defender's window in action". It predicted that "similar findings [will] increase sharply in the coming months".92

Chainguard's overnight rediscovery

On Friday 16 Oct, Chainguard was told only that "something was coming in PHP". That night, CEO Dan Lorenc says, the company found the bugs itself using a frontier model and a "basic prompt of 'find bad vulnerabilities in PHP'".7 This is perhaps the most alarming detail in the whole story: a vague hint plus AI was enough.

The debate: discovery, or very fast rediscovery?

"Yes, AI changed the game"
  • Wiz: "What AI changed was the ability to understand the weaknesses".19
  • Google DeepMind's Raluca Ada Popa: Wiz "has shown why frontier AI is a game-changer for cyber defense."5
  • Wiz co-founder Ami Luttwak called it "the most severe AI vulnerability that was ever found".18
  • Tolmo's Kirov: "finding the flaw and proving what it is worth used to be the same expensive activity. They have come apart."22
"No, humans did the hard thinking"
  • Nick Rogers (Dead Neurons): "Humans noticed the bug in 2004, 2019, and 2024." He adds that "every single piece of PHP2Shell was already sitting in the public training data" and that "unsteered AI models failed to connect the dots on their own."20
  • SmartScope: "Public materials do not establish how autonomously Codex Security operated."21
  • The WSJ noted that much of the risk assessment came from the companies involved.18
Our read: the evidence supports "AI-assisted", not "AI-discovered". Humans picked the target and the old clue. AI made it cheap and fast to turn a known weakness that everyone had shelved into a proven, working danger. The flip side is that the same speed is available to attackers.

05 · The leak

Four cracks in the dam

An embargo is like a surprise party. Everyone involved knows the date but keeps quiet so the guest (here, the attackers) doesn't find out first. PHP2Shell's party was spoiled in four separate ways within about 17 hours.

Crack 1 · The Hacker News post

"source: trust me, bro"

At 15:20 UTC on 20 Oct, user petecooper posted "Tell HN: 2x PHP RCE CVEs with CVSS 10.0 Incoming". It said a reliable source had told him two critical PHP flaws would be announced on 22 Oct at 18:00 CEST. It claimed all versions from PHP 5 were affected, listed both CVE numbers, and urged people to be ready to update. The sourcing line read: "source: trust me, bro".26

Within minutes another user, unreal37, replied: "This was supposed to be embargoed."26 The post was later taken down, but screenshots had already spread.14

The apology

"I unknowingly broke the PHP RCE embargo. I am sorry"

Two days later petecooper posted a public apology. Its key lines:

  • "I am truly sorry."
  • "I take full responsibility for my actions."
  • "It was not remotely my intention to cause any of the subsequent side effects."
  • "I have learned my lesson."

He said his contact had told him there was no embargo.27 Some commenters, including Colin Percival (cperciva), argued that the embargo was already broken before the information reached him. Some guessed at who the source was; nothing has confirmed it.27

Crack 2 & 3 · Confirmation and the video

From rumour to fact

Once watchTowr confirmed the bugs were real, the rumour became news.15 A few hours later Calif "mistakenly published a video" showing its demonstration working "against numerous targets". The Foundation says: "The video contributed to accelerated development of various PoCs".3 Which platform it appeared on, and how long it stayed up, has not been reported. Huntress says only that it was "briefly posted online and then removed."14

Crack 4 · The early patch

Chainguard vs the PHP Foundation

The Foundation: "Chainguard unilaterally broke the embargo and published built images containing the fix… This disregarded weeks of work by many parties toward a coordinated disclosure." It added: "Any attacker could now study the fix in binary form while every other PHP user was still waiting for the release."36

Dan Lorenc: "I made the call to get these out early when exploits hit in the wild." Also: "It's coordinated vulnerability disclosure, unless there's evidence of active exploits in the wild." And: "I'm sorry that my decision led to even more stress for them."67

Unresolved: Lorenc says Chainguard "didn't leak", but he hasn't named the vendors or published the evidence of attacks he cited. Foundation board member Nils Adermann said: "There were no confirmed exploits."67
The mystery · 17 October

Who knew four days early?

Amazon's MadPot is a huge network of fake servers set up to attract and record attackers, a bit like a decoy house wired with cameras. On 17 Oct it caught an attempt to use PHP2Shell, before the leak and before Chainguard's release. Amazon CISO CJ Moses: "The exploit attempt originated from an IP address associated with a commercial anonymization network". He added: "While the vulnerability was under embargo, the targeting of a honeypot from an anonymized IP address suggests the activity was conducted by a threat actor." Amazon says "it remains unclear how the actor acquired exploit information prior to disclosure". An Amazon spokesperson said "there was no evidence" it was harmless.89

Moses's one-line lesson: "An embargo protects defenders only until someone else finds the same bug."8

05½ · The three big questions

How did attackers know? Why unplug to patch? Why could people still lose out?

These are the three questions readers ask most. Here are the answers, built only from what's been reported.

Question 1

How did the hackers find out about a secret bug?

There was no single moment when "the hackers were told". Information reached them through five channels, roughly in this order:

The hint was enough

Once the world knew that PHP had two critical remote-takeover bugs, and roughly where to look, skilled people (and AI tools) could go hunting. Chainguard proved how quickly: given only "something was coming in PHP", it rediscovered the bugs in one night.7 OpenAI's Clint Gibler watched it happen: "a rumor/leak started Tuesday, and then immediately people everywhere began their own vuln hunting".16

The video helped

The Foundation says Calif's accidental video "contributed to accelerated development of various PoCs".3 It proved the attack was real, which is a strong motivator.

The fix itself is a map

This is the counter-intuitive part. Publishing a fix tells attackers what was broken. Comparing old and new code (a "patch diff") points straight at the weak spot. That's why the Foundation was angry that Chainguard's early builds let "any attacker… study the fix in binary form while every other PHP user was still waiting".3 Amazon: "AI-assisted analysis makes it cheaper to turn a patch diff or advisory into a working exploit".8

The ghost remains a mystery

Nobody has explained the 17 Oct probe. It could be a leak from inside the large private group, or someone who found the bug independently. Amazon: "it remains unclear how the actor acquired exploit information prior to disclosure".8

Analogy: a bank says "two of our vaults have a faulty lock; new locks arrive tomorrow". Even without blueprints, burglars now know which building to case. And once the new locks are fitted in public, anyone can see what changed.
Question 2

If a patch existed, why did sites have to go offline to apply it?

A patch isn't a magic button. For a government running hundreds of sites, "applying it" means a chain of jobs, and attacks were already arriving while that chain was being worked through.

  1. Find every PHP site. Big organisations often don't know them all. The NCSC warned: do "not limit discovery to outdated PHP versions".39
  2. Get the right fix. Easy for PHP 8.2 to 8.5. For older versions there were only source-code patches, a volunteer's packages, or nothing at all.7497
  3. Test it. An upgrade can break an old council form or payment page.
  4. Deploy and restart every server, then check that the new version is really the one running.

A site that's switched off can't be attacked. So the safest order was: unplug → patch → check → plug back in. That's exactly what agencies advised. The NCSC said consider "taking the system offline until it can be fully mitigated"39, and KISA said "If even temporary measures are difficult, stop the service."64 Finland's Valtori shut off incoming traffic first and began installing patches around 18:00.53 Canada's minister: "Affected websites will be restored once patches are applied."42

Why so many at once? The bug was in PHP itself, so every PHP site an organisation ran was affected at the same moment. The patch also arrived at 14:00 UTC, evening in Asia and late afternoon in Europe, with attacks already climbing. For many teams, a few hours of planned downtime was cheaper than the risk of a breach.
Question 3

If it was patched, why could some people still lose out?

First, the facts: as of 26 Oct there was no confirmed public breach through PHP2Shell. One claimed government case was retracted.32 But "patched" doesn't automatically mean "safe", and some losses were real. Here's why:

🚪 Burglars already inside

Patching changes the lock but doesn't remove someone who got in earlier. Attempts began on 17 Oct, before any patch existed. That's why the NCSC and Amazon say to check for backdoors going back to 17 Oct.398

🔑 Copied keys still work

One bug could leak server memory, including passwords and keys. If those were copied before the patch, they keep working until they're changed. Hence the advice to rotate secrets.9486

🔄 "Patched" but not really

The new version only protects you once PHP is fully restarted and the right configuration is in use. A half-done update leaves the old, vulnerable code running.30

🧓 Too old to patch

PHP 5.4 to 7.3 got no official fix. Bitsight found only about a third of the PHP versions it identified were covered by the update. Forgotten old servers stay exposed.7475

3️⃣ A third bug

CVE-2026-115560, disclosed on 23 Oct, affects even fully patched releases, and a fix is waiting for the next regular release.102

⏸️ The cost of switching off

The shutdowns themselves were a real loss. Dutch citizens couldn't use DigiD, Japanese bank and airline services were limited, schools lost Aula and Smartschool, and two long-running Japanese games announced shutdowns over the issue.516562

Two smaller, concrete "losses": the Steal My Bitcoin challenge, a deliberately unpatched server, lost its ~$2,021 prize on 25 Oct, which showed the attack can work against old code.83 And curious people who ran fake "exploits" from GitHub got pranked.33

06 · The global response

The day governments unplugged themselves

The most unusual part of PHP2Shell is that the sites went dark because their owners switched them off, not because hackers knocked them down. It's like closing the shop and pulling down the shutters while a locksmith changes the locks.

08 · The threat actors (news level)

From a trickle to a flood

First, to be clear: the people who found PHP2Shell were the good guys. The "threat actors" are the people who rushed to use it once it leaked. Here's what reporting says about who they were and how fast they grew. It's kept at headline level on purpose.

The ghost · 17 Oct

One quiet early probe

A single attempt on Amazon's decoy servers, sent through a commercial anonymisation network. No actor has been named. It's the only sign that someone may have had inside knowledge (see chapter 09).8

Suspected North Korea

CYFIRMA's "staging" campaign

Threat-intelligence firm CYFIRMA reported a suspected North Korean state-linked operation. It used 21 hijacked scanning servers and narrowed its list to 216 target hosts. Targets included government, banks, ports, aviation, manufacturing and trading platforms in the US, Japan, South Korea, Thailand, Indonesia, Australia, Taiwan, India, Singapore, the UAE, Saudi Arabia and the EU.31

CYFIRMA gave moderate confidence to a link with the wider Lazarus ecosystem. That rests on language and working style, with no shared infrastructure or malware. Its words: "No launch date has been stated." Amazon made no nation-state attribution, and no government has confirmed one.3110

The swarm

Many hands, mostly failing

Chainguard's decoys caught traffic from China and Russia.7 ELLIO saw senders on Chinese, Hong Kong, Indian and European hosting networks, carrying test web shells, a remote-access tool and a DDoS kit.13 Fastly counted about 250,000 requests from about 3,200 IPs by midday on 22 Oct. That figure includes defenders scanning their own systems.36 Pantheon blocked more than 60,000 suspicious requests on day one.9

Botnets & pranksters

Old gangs, new trick

Sophos saw operators of "Potassium", a variant of the Mirai botnet, try PHP2Shell. The attempt was blocked, and Sophos corrected an earlier report that it had succeeded.34 On GitHub, fake "exploits" appeared, including one that only changed the victim's wallpaper to NSFW images.33 Underground forum users mocked most public exploit code as "AI slop", posting: "PoC yes. RCE no."76

Did anyone actually get breached? As of 26 Oct, no confirmed public case. Palo Alto's Unit 42 linked an attack on a European government entity to PHP2Shell, then retracted it: "We are unable to confirm that initial access is associated with the specific PHP2Shell CVEs."32 Hunt.io tracked 123 targeted servers and found none exploited.34 Amazon, however, says "PHP2Shell is now being broadly exploited in the wild", so attempts are widespread even though confirmed successes are not.34

12 · The India angle

Advisories, targets, and one unrelated ransomware attack

India didn't see the dramatic government shutdowns that Europe did, according to the reporting we found. But it was on attackers' target lists, CERT-In issued a critical note, and the same week brought a separate ransomware attack on a Telangana portal.

CERT-In · CIVN-2026-0510

"Critical remote code execution vulnerabilities in PHP"

  • Issued: 21 Oct 2026. Last updated: 26 Oct. Organiser.org dates it 22 Oct.46101
  • Severity: Critical. Risk: High.
  • What it says: "These vulnerabilities exist in PHP due to memory corruption and improper resource control. A remote attacker could exploit these vulnerabilities by sending a specially crafted request to the targeted system."
  • Update: "Multiple reports confirm large scale exploitation in the wild, users are advised to patch urgently."46

CERT-In is India's national computer emergency response team, under MeitY. We found no separate MeitY or NIC statements and no named Indian victims. One outlet reported "no Indian victim names yet".105

India on the target list

Where India shows up in the threat data

  • India was among the priority countries in CYFIRMA's suspected North Korean target set.31
  • ELLIO saw some attack traffic coming from an Indian internet provider's network. That's common, because attackers rent or hijack servers everywhere.13
  • India has a huge PHP footprint. Many state portals, universities and small businesses run WordPress and similar systems, so the "update your PHP" message applies widely.
Separate incident

Telangana's TG-iPASS portal hit by ransomware

TG-iPASS is Telangana's single-window portal for industrial approvals. At about 11:36 pm on 22 Oct, the database server (hosted by Cloud4C) stopped connecting. Officials found the database and related files encrypted and renamed with a ".vgb" ending.4847

The ransom note left only a contact email and a machine ID, and named no amount. The Telangana Cyber Security Bureau (TGCSB) registered a case under IT Act Sections 43 and 66, on a complaint from Joint Director of Industries Sanga Suresh. A senior official admitted the existing security measures were unsatisfactory.48

On 25 Oct, Andhra Jyothy reported the portal restored, with officials saying "the information is safe on the server". Director Nikhil Chakravarthy said security was being strengthened "to prevent such incidents from recurring". Telangana Today, updated 26 Oct, still described restoration as in progress.4947

Is it linked to PHP2Shell? No source makes that link. None of the reports mention PHP, and the affected server is described as running Microsoft SQL Server. It's mainly a coincidence of timing.4847 Also unrelated: on 16 Oct, CERT-In and others alerted SBI to customer data on the dark web (3,897 records containing personal data, out of about 3.75 lakh analysed). SBI said there was "no material impact on its core operations".50

13 · For ordinary people & site owners

Should I worry? What should I do?

FAQ for everyone

Is my personal data at risk?
Only if a specific service holding your data was breached. As of 26 Oct, no confirmed company or government breach through PHP2Shell had been made public.8532 The bug is in web servers, not in your phone or laptop.
Do I need to update my phone or computer?
No. "You don't need to do anything on your phone or computer."84 Keeping your devices updated is still good practice in general.
Should I change my passwords?
Only if a service tells you it was breached. Using a password manager and unique passwords protects you either way.84
Why did government websites disappear?
Mostly by choice. Agencies like the UK NCSC, the NSA and Germany's BSI advised taking sites offline if they couldn't be patched right away, the way you'd shut the shop while the locks are changed.3955
I got an email saying "urgent PHP security update, click here". Is it real?
Treat it as phishing and delete it. Scammers jump on big news.84
Was AI used to attack me?
AI helped find the bug. Experts warn that AI makes it faster to turn patches into attacks, but no source has confirmed that attackers used AI to exploit PHP2Shell.8
Is it over?
Mostly, for well-run sites. A third related bug (CVE-2026-115560) still awaits a fix, and old, unmaintained sites will stay at risk for a long time.10275

✅ Website owner checklist

A plain summary of the official guidance from the PHP Foundation, NCSC, CISA, Amazon and Cloudflare. Follow your host's and your national CERT's advice first.

  1. 1
    Find out which PHP you run. Check every site, including the forgotten ones. The NCSC says not to limit the search to outdated versions.39
  2. 2
    Update to 8.5.12, 8.4.27, 8.3.36 or 8.2.35 or later. On older versions, use your host's or distribution's backport, or upgrade.397
  3. 3
    Restart PHP fully so the new version is actually running. Make sure you changed the configuration your web server really uses.30
  4. 4
    Can't update today? Put the site behind a web application firewall, or take it offline until you can. PHP says no configuration change alone covers both bugs.1274
  5. 5
    Apply the interim workaround for the third bug that your CERT or host recommends, until the next PHP release.4041
  6. 6
    Check for intruders. Patching locks the door but doesn't evict anyone already inside. Look for unexpected new files, processes and admin accounts, going back to 17 Oct.839
  7. 7
    Rotate secrets such as database passwords, API keys and app keys once you've finished checking, because one bug can leak server memory.8694
  8. 8
    Ignore random exploit code on GitHub. Some of it is fake or malicious.33
14 · The bigger lessons

What PHP2Shell tells us about the next ten years

1 · AI vs AI

The window is shrinking

Amazon: "AI-assisted analysis makes it cheaper to turn a patch diff or advisory into a working exploit."8 Prince expects "a year or two where every week it feels like the sky is falling".37 Defenders now have to patch in hours, not weeks.

2 · Fund the foundations

Billions on top, pennies underneath

The Foundation's 2025 contributions were $730,534 from 536 sponsors, fewer than the year before.71 The Guardian contrasted its small staff with the "billions" going into AI.2 The Sovereign Tech Agency, which paid for the 2024 audit, says "too little funding goes into maintaining it."69 The Foundation is now asking companies, hosts and governments for sponsorship, and has switched from consensus to majority voting on security decisions.3

3 · Does secrecy still work?

The embargo debate

Art Manion (FIRST) says this "leads us to reconsider the risk reduction value of long coordinated vulnerability disclosure embargoes".16 InfoWorld called it a weakness in the whole system.72 The counter-argument: without the embargo there would have been no patch ready at all. The likely future is shorter embargoes, smaller circles and faster releases.

4 · Memory safety

The C question

Both bugs are the kind of memory mistake that languages like Rust and Go are designed to prevent.24 Rewriting PHP's engine isn't realistic soon, but the case for safer languages in new core infrastructure got stronger.

5 · Research is catching up

Small models can do it too

An arXiv paper from July 2026 (HoF-Bench) found that a minimal AI analyser without frontier models rediscovered up to 65 of 95 AI-found CVEs. Its misses clustered in C infrastructure code like PHP's.88 AI bug-finding is spreading fast, to defenders and attackers alike.

"An embargo protects defenders only until someone else finds the same bug."CJ Moses, Amazon CISO8
15 · Jargon buster

Glossary

PHP
A programming language that builds web pages on the server. Its mascot is a blue elephant.
PHP2Shell
The nickname for CVE-2026-109618 and CVE-2026-109619, coined by Wiz.
CVE
"Common Vulnerabilities and Exposures": an official ID number for a known security bug.
CVSS
A severity score from 0 to 10. Anything 9.0 or above is "critical".
RCE
Remote Code Execution: getting someone else's computer to run your commands over the internet.
Shell
A command line. "Getting a shell" means getting control.
Out-of-memory (OOM)
When a program uses up its memory allowance. PHP's abrupt stop when this happened is the root of PHP2Shell.
Use-after-free
A program keeps using memory it has already handed back, like a hotel key that still works after you check out.
Embargo
A private period when finders and fixers keep a bug secret until the patch is ready.
Coordinated disclosure
The process of reporting a bug privately, fixing it, then announcing it to everyone at once.
Zero-day
A bug attackers can use before any fix exists.
Proof of concept (PoC)
A demonstration that an attack really works.
Patch diff
The before-and-after comparison of a fix. Attackers study it to work out what was broken.
Honeypot
A decoy server that attracts and records attackers, like Amazon's MadPot.
WAF
Web Application Firewall: a filter that blocks bad requests before they reach a website.
Backdoor / web shell
A hidden way back in that an attacker leaves behind.
Botnet
A network of hijacked machines controlled together. Mirai is a famous family.
End-of-life (EOL)
A software version that no longer gets official updates.
Backport
Taking a fix from a new version and applying it to an older one.
CERT / CSIRT
A national or organisational cyber emergency team, such as CERT-In, NCSC or CISA.
Ransomware
Malware that locks your files and demands contact or payment, as in the TG-iPASS case.
Lazarus Group
A hacking group widely linked to North Korea.
Frontier model
One of the most capable AI models available, such as GPT-5.6 Sol or Gemini 4 Argon.
Memory-safe language
A language like Rust or Go that prevents whole classes of memory bugs.
